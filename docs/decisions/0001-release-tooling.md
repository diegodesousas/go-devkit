# 1. Cut releases from a make target, not from a release automation tool

## Status

Accepted — 2026-08-13

## Context

go-devkit went from `v0.0.1` (2026-05-08, the `init` commit) to a `main` branch
carrying 35 unreleased commits, among them eight behaviour fixes in `pkg/` — for
instance `tx.Exec`, which used to return `nil` on the success path and now
returns the actual `sql.Result`. Because the Go module proxy only sees tagged
commits, every consumer of the library was pinned to the May snapshot. Cutting a
version was a manual, repeated, easy-to-get-wrong sequence.

We wanted one command that computes the next version, refuses to release from an
invalid state, and publishes the tag plus a GitHub Release.

The obvious move was to adopt an existing tool. We evaluated:

| Tool | Assessment |
|---|---|
| [svu](https://github.com/caarlos0/svu) | Closest fit. Prints the next version from the git log; would replace our version computation and nothing else. |
| [release-please](https://github.com/googleapis/release-please) | Maintains a release PR, writes `CHANGELOG.md`, tags and publishes on merge. Changes the workflow from "run a command" to "merge a PR". |
| [GoReleaser](https://goreleaser.com/cookbooks/release-a-library/) | With `builds: [{skip: true}]` it releases a library without binaries, but it does not create the tag — it needs one to already exist. |
| [go-semantic-release](https://github.com/go-semantic-release/semantic-release) | Publishes on every push to `main`. No human checkpoint. |
| [git-cliff](https://git-cliff.org/), [cocogitto](https://github.com/cocogitto/cocogitto) | Solve changelog generation, which is not our problem. |

All of them derive the version bump from Conventional Commits. Our history does
not support that. Between `v0.0.1` and `v0.1.0` the commits were:

```
7 fix   5 style   3 chore   2 test   2 docs   1 refactor
```

Zero `feat:`. Every one of these tools would have computed `v0.0.2`. The version
we actually wanted was `v0.1.0`: pre-1.0, a minor absorbs accumulated behaviour
changes without promising the API stability this library does not yet offer.
That judgement is not recoverable from commit messages.

## Decision

Keep the release flow in the `Makefile`, as two targets:

- `make next-version [BUMP=…]` — prints the computed version, writes nothing.
- `make release [BUMP=…]` — validates, tests, tags, pushes, publishes.

The version is derived from the latest tag, with `BUMP` ∈ `patch` (default),
`minor`, `major`, and `VERSION=v1.2.3` as an explicit override. The human picks
the bump; we do not infer it from commits.

`make release` aborts before creating anything when the branch is not `main`,
the working tree is dirty, `HEAD` has diverged from `origin/main`, the tag
already exists locally or remotely, or `BUMP`/`VERSION` is malformed. Only then
does it run `make test`, `make lint`, create the annotated tag, push it, and
call `gh release create --generate-notes`.

Integration tests are deliberately excluded so that cutting a release does not
require a running Docker daemon.

## Consequences

- No new dependency. The release path needs only `git`, `make` and `gh`, all
  already required by the existing workflow.
- Choosing the bump stays a deliberate human act. This is a feature while the
  library is pre-1.0 and commit types under-describe the real impact of a
  change, and a cost once releases become frequent.
- No `CHANGELOG.md` in the repository; release notes are generated by
  `gh --generate-notes` from the merged PRs.
- Roughly 50 lines of shell in the `Makefile` are ours to maintain. The version
  arithmetic is covered by `make next-version`, which is side-effect free and
  can be exercised without creating tags.
- Should the project start receiving `feat:` commits regularly, adopting `svu`
  becomes defensible: it would replace `next-version` alone, leaving the
  validations, tagging and publishing in `release` untouched.

First release cut this way: [v0.1.0](https://github.com/diegodesousas/go-devkit/releases/tag/v0.1.0).
